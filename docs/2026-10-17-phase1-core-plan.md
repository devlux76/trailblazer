# Trailblazer Phase 1 (the core) Implementation Plan

> **Historical (2026-11-01):** implemented; its unchecked boxes are stale tracking, not open work.
> Open work is in `docs/2026-10-23-design-review.md` and the git-bug issues.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **This plan's execution (operator's decision):** each task is drafted by MiniMax M3.1 Flash (OpenCode, model variant `max`) and reviewed by Codex. Claude directs and verifies. The C/C++/CUDA/Go and vendored-directory follow-up is implemented and verified by Codex (VORTEX handoff, 2026-10-18).

**Goal:** A running Elixir service that knows a repository's land, its definitions, how they use each other and which design sections they implement, and answers `where_declared`, `who_uses`, `impact_of`, `read_range`, `search` and `trail` from a CLI, so that Claude and Codex can use it in place of the ranger skill.

**Architecture:** An OTP application `:trailblazer` in its own repository. Parsers turn files into definitions and references (Elixir's own parser; tree-sitter in a Rust program behind an Erlang Port for JS/TS/Python/C/C++/Go; a Markdown reader for design documents). A resolver links references to definitions; SQLite holds nodes and edges; Qdrant holds one vector per definition, keyed by the node's id. One indexer process per repository keeps all of it current. Queries and the trail read SQLite and Qdrant. A loopback HTTP API serves an escript CLI.

**Tech Stack:** Erlang/OTP 29.1.1 and Elixir 1.20.4-otp-29 (`.tool-versions`, via mise); deps at latest: `exqlite`, `req`, `jason`, `bandit`, `plug`, `file_system`; Rust (cargo 1.93) with the `tree-sitter`, `tree-sitter-javascript`, `tree-sitter-typescript` `tree-sitter-python`, `tree-sitter-c`, `tree-sitter-cpp` and `tree-sitter-go` crates at latest; ripgrep; EmbeddingGemma 2 on `:8091`; Qdrant 1.19 on `:6333`.

**Spec:** `docs/trailblazer/design.md` in the mirai-agent repository (§6 is this phase; §11 phase 1).

## Global Constraints

- Dependencies at latest while developing; pin only at release.

- Files: `rg --files --no-require-git` in the repo (honours `.gitignore`); skip empty files and files over 400,000 bytes; parse by suffix: `.ex .exs` (Elixir), `.js .jsx .mjs .cjs .ts .tsx` (tree-sitter), `.py` (tree-sitter), `.c` (C), `.h .hh .hpp .hxx .cc .cpp .cxx .cu .cuh` (C++ including CUDA), `.go` (Go), `.md` (design documents). A second `rg --files --no-ignore` pass includes ignored `deps/`, `vendor/`, `vendored/` and `third_party/` trees; both passes exclude `node_modules/`, `_build/` and `target/` and deduplicate paths.
- State directory: `~/.local/share/trailblazer/` (SQLite file `trailblazer.db`, `endpoint.json`). Tests use a temporary directory.
- API on `127.0.0.1` only; `endpoint.json` holds `{"url", "token"}`, mode 0600; every request carries `authorization: Bearer <token>`. Never log the token.
- Token estimates: 4 characters per token.
- For every parser, a node's `text_hash` is the hex sha256 of its source lines `start_line..end_line`, and its `signature` is its first source line, trimmed, at most 200 characters, unless a task says otherwise. Both are computed in Elixir.
- Tests: `mix test` is hermetic (no network, no services). Tests that need the embedder or Qdrant carry `@tag :live` and are excluded by default; `mix test --only live` runs them.
- Each task ends with `mix format --check-formatted`, `mix compile --warnings-as-errors` and `mix test` green, then a commit, then `python3 ~/.agents/skills/ranger/index.py -C /home/mirai/projects/trailblazer` so ranger's index of this repo is current. ## Review Focus

- **A file with a syntax error** (Elixir mid-edit): the file's previously indexed nodes stay, marked `stale`, until it parses again; the rest of the repo indexes normally (Task 3, Task 8).
- **The same qualified name defined in two files** (a module duplicated in test support, two `index.ts`): both definitions are kept as separate nodes; a reference to the name gets an `uncertain` edge to each (Task 6).
- **Embedder or Qdrant down:** the graph still indexes and every query except vector search works; vectors wait in a pending queue and the trail says `"no vectors"` (Task 7, Task 10).
- **A file deleted or renamed:** its nodes, edges and points go; edges that pointed into it from other files become unresolved references, not dangling ids (Task 8).
- **`read_range` given `../`, an absolute path outside the repo, or a symlink leading out:** refused with nothing read (Task 9).
- **Containment holds for TRUSTED repos only; hostile concurrent writers are out of scope for phase 1.** `Files.read/3` resolves the path, refuses anything out of the repo, reads, then resolves again and compares the file's identity (`major_device`, `inode`), throwing the content away if either moved. The bytes are read before that second check, so the check narrows the window but does not establish containment: a directory inside the repo can still be swapped for a symlink to somewhere outside it between the two checks, and a swap that puts the same file back can pass both. Real containment needs descriptor-bound resolution — `openat2` with `RESOLVE_BENEATH` — in the Rust Port. Until that exists, Trailblazer reads repositories its operator trusts, and nothing else.

### Task 1: Project, configuration and store

**Files:**
- Create: `mix.exs`, `.tool-versions`, `.formatter.exs`, `.gitignore`, `README.md`, `NOTICE` (copy `docs/coder/NOTICE` from mirai-agent, "Coder" → "Trailblazer"), `lib/trailblazer/application.ex`, `lib/trailblazer/config.ex`, `lib/trailblazer/store.ex`, `priv/migrations/001_graph.sql`
- Test: `test/trailblazer/store_test.exs`, `test/test_helper.exs`

**Interfaces:**
- Produces: `Trailblazer.Config.get(key)` for `:state_dir`, `:embed_url`, `:embed_model`, `:qdrant_url`, `:api_port` (default 7900), `:trail_tokens` (default 4000).
- Produces: `Trailblazer.Store` (a GenServer owning the one writing exqlite connection) with:
  - `add_repo(path) :: {:ok, repo_id}`; `repos() :: [%{id, path}]`
  - `replace_file(repo_id, path, %{hash, nodes: [node_attrs], refs: [ref_attrs]}) :: :ok`, atomically replacing everything that file contributed
  - `mark_stale(repo_id, path) :: :ok`; `delete_file(repo_id, path) :: :ok`
  - `put_edges(repo_id, [edge_attrs]) :: :ok`, replacing the repo's resolved edges
  - `node(id)`, `nodes_by_name(repo_id, name)`, `nodes_by_qualified(repo_id, qualified)`, `nodes_in_file(repo_id, path)`, `edges_from(ids, kinds)`, `edges_to(ids, kinds)`, `refs(repo_id)`
  - `pending_vectors(repo_id, limit) :: [node]`; `vector_done([{id, text_hash}])`, which records the hash that was embedded, not the node's current one: a node indexed again while its embedding was in flight stays pending
- Node attrs: `key` (text, unique per repo: `"<lang>:<kind>:<path>#<qualified>"`), `lang`, `kind` (`module | function | macro | type | test | class | method | doc_section`), `name`, `qualified`, `path`, `start_line`, `end_line`, `signature`, `text_hash`, `stale` (bool), `vector_hash` (hash last embedded, or nil). A node's integer `id` is its row id and stays the same while its `key` exists; it is also its Qdrant point id.
- Ref attrs (unresolved, as parsed): `from_key`, `kind` (`calls | references | imports | aliases | uses | tests | implements`), `target` (one string: qualified name, path, or doc citation), `arity` (or nil), `line`, `ambiguous` (bool, default false; one ref per candidate when true).
- Edge attrs: `from_id`, `to_id`, `kind`, `uncertain` (bool), `line`.

**Edge-case register (operator's rule, 2026-10-18).** Every edge case found anywhere in this build is added here when it is found, as a class with its first repro, the tasks it touches, and its status. Statuses: **tested** (a checked-in regression test holds exactly this claim); **documented** (an accepted limit, stated in Review Focus); **OPEN failing** (observed wrong today); **OPEN untested** (believed to work, but no test holds it); **OPEN prospective** (a test or decision owed by a task not built yet). Before any task is handed out, its brief carries a *forward* list: the classes below that apply to it, each turned into a test of that task. Both Claude and Codex audit this register; theoretical edge cases become common cases in practice.

*A. Input text and encodings*
- A1. File names containing a newline (`line\nbreak.ex`): list with NUL separators. Task 2, tested.
- A2. A definition head spanning lines: the signature is collapsed to one line. Task 3, tested.
- A3. Byte-order mark at the start of a file: Markdown, citations and the Elixir parser drop it before reading; line numbers are unchanged and `text_hash` keeps the raw bytes. Tasks 3, 5, tested; tree-sitter copes.
- A4. Bytes that are not valid UTF-8 (a Latin-1 comment): `TreeSitter.parse` returns `{:error, :invalid_encoding}` before encoding, and the same GenServer takes the next call (Task 4, tested). Markdown and citations replace such bytes before reading, so names stay valid UTF-8 and `text_hash` keeps the raw bytes (Task 5, tested). Elixir rejects invalid encoding as a parse error, which is correct; Task 8 keeps the file's stale nodes after any parser error.
- A5. Look-alike characters (` for ', smart quotes, non-breaking space, `§` written as `S`/`&sect;`): a parser never crashes on them and never invents a match from them. Citations: tested (`S1`, `&sect;2` are not citations). Other readers, **OPEN untested**.
- A6. CRLF line endings: Markdown and citations give the same sections, ranges and lines as LF (tested). Line numbers, `text_hash`, `read_range` and trail excerpts must agree on raw versus normalised lines; decide once. Tasks 3, 4, 8-10, **OPEN untested**.
- A7. A closing code fence is the whole line: the opening run of marks, at least as long, then only spaces or tabs (CommonMark 4.5). ```` ```not-a-close ```` inside a fence is text; it closed the fence, indexed a fake heading inside it and hid the real one after it. Task 5, tested (backtick and tilde fences).
- A8. Text is read against the plan's stated rule, not a narrower one: `## 7)Overview` and `## 8.Title` are sections `7` and `8` (were `7-overview`, `8-title`); `## 2026plans` is a slug. Tasks 5, 6, tested.
- A9. Delimiters inside identities are data: Elixir `contains` targets carry the definition's qualified attribute directly, including for `lib/a#b.ex` (Task 3, tested). Escaping or structure for `spec#name` and the CLI's `path:line` remains **OPEN prospective** for Tasks 6, 9, 12.

- A13. Vendored directories remain listed despite `.gitignore`; the normal and no-ignore vendor passes merge without duplicates. node_modules, _build and target output stay out in both passes; suffix, empty and size rules still apply. Task 2, tested.

- A15. - B2. Calls inside call arguments are refs too (`Outer.f(Inner.g())`). Task 3, tested.

- B4. Nested `defmodule` binds its implicit alias; `__MODULE__.Child`, grouped multi-segment aliases, `&__MODULE__.f/2` resolve. Task 3, tested.

*C. Order and position*
- C1. Combined query results are put in source order before qualifying and attaching. Task 4, tested.
- C2. A reference after a definition has ended belongs to the enclosing one, not the ended one. Task 4, tested.
- C3. A citation inside a definition comes from it (module → function); outside every definition `from_key` is nil. Task 5, tested.
- C4. Query literal-hit ownership still needs persisted source order after stable-id upserts: index `z; a` on one line, then reorder to `a; z`; SQLite row/id order remains `z,a`, so a trailing literal hit incorrectly selects `a`. Task 9, **OPEN failing**, reproduced 2109f6a. Definitions sharing a line range need an ownership rule: `def f(a, b \\ 1)` gives `f/1` and `f/2` on the same lines, and a citation in the body goes to whichever came first, while Task 3 gives the body's calls to the declared head. Several definitions on one line have the same problem. Rule: of the narrowest definitions holding a line, the last one listed. That is sound only because every parser lists nodes in source order (line, then column), with default-argument heads before the declared head, so the last is the one credited with the body (`g/10` over `g/9`; `a` after `z` on one line, Codex's repros). The Elixir parser holds that order across every kind (`def f; @type t` and `def f; defmodule N` on one line, Codex's repros of 696e778); citations: tested. Tasks 4, 6, 9 apply the same rule, **OPEN prospective**.

- C5. C/C++ function definitions span their bodies, including pointer/reference returns, so calls belong to the function. Header prototypes and forward class declarations are not definitions. A typedef names its struct without becoming its enclosing namespace. C/C++ share bare-name candidates; includes prefer the including directory, then root, then suffix matches (ambiguous matches stay uncertain, capped at eight); header-only files have file nodes. Tasks 4/6/8, tested.

- D14. The loop sorts what goes wrong: the model down or an HTTP error ends the task at once (`failed`, nothing to retry against); a reply cut off at the length limit, a reply with no blocks or blocks that do not parse or apply, a failed or timed-out check, and a failed review each use up an attempt and say why in the next prompt; an unclear review is asked once more; a crash anywhere ends the task `failed` with its record closed (E16). A record that cannot be written stops the task rather than leave a partial case. Phase 2 L7, tested.
- D17. A model names files loosely. A block creating a file keeps its name. The prompt says to use paths exactly as shown. Harness, not model. Phase 2 L2/L7/L10, tested.
- D18. The loop must not go on past a broken step: a reviewer reply cut off at the length limit that says PASS is not approval; a worktree that cannot be reset stops the task (the next attempt would build on the last one's edits); a provision that fails stops it; and a crash report still names the worktree and branch that survive. - D21. The trail fills its budget whatever the task needs. - D10. Model HTTP 200 is not completion: a streamed reply needs valid choices, a finish reason and DONE, plus content or complete tool calls. *J. Time and events (phase 2b, design §13; written before B1)*
- J1. Order: two events published by one process reach every subscriber in that order; events from different publishers have no order and no code may assume one.
- J2. Subscribe then replay: a follower that reads the record so far and then listens must subscribe first, or an event recorded between the read and the subscription is lost; it may then see one event twice and must drop it by sequence number.
- J3. A subscriber that dies, or one that is slow, never blocks or kills the publisher; a slow one's mailbox is its own problem, and long-lived subscribers are bounded consumers (they ask for work) wherever events can come in bursts (a branch checkout touches thousands of files).
- J4. Taking longer is not failing: a reply after a backstop fired is still a reply. The backstop's outcome stands (the attempt is failed, recorded), and the late reply is recorded as late, never applied twice or dropped silently.
- J5. A backstop and the answer can race: disarm after the answer arrives may find the backstop already fired. Exactly one outcome wins, decided in one process, and the other is recorded.
- J6. One investigation per open fault: the same {kind, subject} firing again while its anomaly is open adds to its count, not a new VORTEX message; after an ack, the next firing is a new anomaly.
- J7. The death of the thing waited on is an answer at once (monitor), not a backstop firing later: the model client's process dying, a check's process group exiting, a Port closing.
- J8. Load is evidence: every anomaly carries load average, available memory and swap in use, and who held the model and the embedder, so "the machine was busy" can be told from a fault without asking.
- J9. VORTEX itself down or slow must not stop the work: the investigation request is sent asynchronously, recorded as unsent when it cannot be, and retried when VORTEX is back (on its own event, not a timer).
- J10. One watcher for many repositories: a change in `/a/b` must go to repository `/a/b`, not `/a` (longest root first); a repository nested in another is watched once.
- J11. An event during a sync is the next batch, never lost: the dirty set is swapped out at the start of a sync, so a file changed while it is being read is synced again.
- J12. Up/down flapping: the embedder going down and up repeatedly produces one event per change of state, and queued work resumes on the up event without a retry timer.
- J13. A writer that dies mid-batch loses nothing that was acknowledged: a batch is acknowledged to its producers only after its transaction commits; unacknowledged work is re-queued by the producer on the writer's `:DOWN`. B7 tests controller death after commit but before its acknowledgement, cancellation rollback, and the next queued batch resuming. Review follow-up: killing the Erlang worker alone left a native recursive SELECT and its earlier write lock alive; an independent cleanup owner now cancels execution, rolls back and closes even if DBConnection skips its disconnect callback. A replacement waits for worker, pool, driver and cleanup owner to exit. A writer opened by a new controller also waits for the prior writer cleanup owner. No SQLite lock retry clock: busy_timeout is zero, unexpected contention records a store_busy anomaly with the querying connection and unknown external holder. Native-statement cancellation and controller death are tested.
- J14. A parse worker or Port that dies fails its own file (marked unparsed, recorded), never the batch or the indexer; the pool restarts the Port and takes the next file. B8: the pool is `parse_workers` parsers (default 2), each a process owning one tree-sitter Port, and the FIFO queue of waiting callers; a caller waits with `:infinity`, is dropped if it dies while queued, and has its answer discarded if it dies mid-parse while its parser finishes. The 30 s parse `receive ... after` and the 120 s call timeout are gone: each parse arms one backstop (`backstop_parse_ms`, default 300 s, evidence `%{path:, lang:, bytes:}`), and only the backstop gives up — it closes the Port, answers `{:error, :timeout}` to that one file, records the anomaly, and the next file opens a new Port; a Port that answered or died wins unless its backstop fired in the same moment. A worker or Port that dies answers `{:error, :parser_crashed}` to its own file only, and the pool replaces the worker and keeps serving the queue. What a parser is doing is published on `:parse` (`{:started, path, worker, os_pid}`, `{:ended, path, worker, outcome}`). Tested: two files parsed at once by two parsers, a parser killed mid-file with one file queued behind it, a parse held past its backstop, and a queued caller that dies.
- J15. A reader beside a writer must see one moment: a whole-graph read (`graph_snapshot`, the resolver) on a WAL reader connection holds one read transaction for all its queries, or it can mix rows from before and after a commit (Codex's review of §13, for B7). B7 wraps every reader operation in a deferred transaction; a held snapshot stays coherent through a concurrent commit, tested.
- J16. Replay must be idempotent: when a writer dies between commit and acknowledgement, the producer re-sends a batch that already landed; applying it again must change nothing (Codex's review of §13, for B7/J13). B7 keeps one durable payload fingerprint per current file/edge batch, in the same transaction as the data; replay after reopening the database retains reference and edge ids. Stale/deleted files and changed parser payloads invalidate it, tested. B5 too: a watcher's rescan waits until its native watches are established, or a change during startup is lost.
- J17. A watcher process starting is not native readiness. After reconfiguration, wait for inotify's `Watches established.` before asking every indexer to rescan; retain stderr and child exit diagnostics when startup fails. Reap the old native child before starting a replacement so even reconfiguration does not consume two instances. B5, tested.
- J18. A shared kernel queue can overflow during a burst: report one watcher_overflow anomaly and rescan every member rather than silently lose updates. Retired watcher generations do not route events. B5, tested. Native startup prunes the same `.git`, node_modules, _build and target directories as file listing; deps/vendor remain watched. On this inotifywait `--exclude` filters events but does not save initial watches, so explicit `@path` exclusions prune recursion (real fixture: 12 watches reduced to 4). Capacity failures record kernel limits and requested directory count. Already queued additions share one replacement. Malformed records after readiness trigger an overflow rescan. B5 follow-up, tested.
- J19. A request must be answered by a reconcile that started after it arrived. A reconcile already running may have listed or stat'ed the file the caller just saved; joining it would answer from the old text. Waiting requests join the next reconcile; one reconcile answers all that were waiting when it began (design §13.7).
- J20. Changes come from git (operator: "just track git", design §13.7): committed changes from a diff of the indexed HEAD against HEAD, working-tree changes from `git status --porcelain=v2 -z --untracked-files=all`, whose index stat cache already handles racy timestamps and restored mtimes. Only a directory that is not a work tree falls back to a stat tuple (size, mtime_ns, ctime_ns, inode), because (size, mtime) alone misses `cp -p`, `rsync -t` and `touch -r`.
- J21. Reading git must never get in the way of a git command: every git call runs with `GIT_OPTIONAL_LOCKS=0` (measured: status then writes nothing under `.git`), never takes `index.lock`, and never writes refs, config or the index. A command that fails because the operator's git holds a lock is retried on the git-directory event that follows the lock's release, not on a timer.
- J22. A repository root that vanished, moved or stopped being a work tree answers the request with an error naming it, never a stale answer from the store.
- J23. A large change in a cold repository (branch switch, a pull of thousands of files) makes the request wait for the whole reconcile: progress streams on `{:repo, path}` and one backstop guards it; the caller sees files reconciled, not silence.
- J24. The indexed HEAD can stop existing (a rebase, an amend, a reset, then gc) or HEAD can be unborn (no commits yet), detached or shallow. When the diff from the indexed HEAD fails, reconcile from `git ls-files -z` plus status against every path in the store (a full listing compare, still no re-read of unchanged files by blob id); an unborn HEAD is all untracked. Linked worktrees watch their own `.git/worktrees/<name>`; a submodule is its own repository.
- J25. Ignored but indexed directories (deps/, vendor/: operator's request) are invisible to status. Their lockfile (`mix.lock`, `bun.lock`, `package-lock.json`, `Cargo.lock`, `poetry.lock`, `go.sum`) is tracked; a change to it rescans that directory by stat tuple. With no lockfile, the directory is rescanned by stat on each request.
- J26. One watch per repository is still a resource: the instance count is 1 for the whole service, the watch count one per repository (plus one per linked worktree). ENOSPC on adding a watch records one anomaly naming the limits; that repository stays correct, reconciling on each request only.

A restart restores every watched repository, and each reconciled and embedded at once: 22 repositories at boot is the whole machine (deployed service, 2026-10-19; the first restart full-synced 15 never-indexed ones in ~6 min and then embedded all of them). Operator: index what is asked for, and let git trigger the rest. Status says `deferred`. An explicit `watch` indexes at once. Test "J27: a deferred watch reads and embeds nothing until asked".
- J28. Loading a whole graph to answer a small question: each indexer's init loaded every node to find stale paths, every sync to find module paths, every status to count nodes and edges. With 22 repositories (llama.cpp, Babylon.js among them) a boot read 11.6 GB and grew to 6.5 GB RSS before answering anything (deployed service, 2026-10-19). Each is now one query: `Store.stale_paths/1`, `module_paths/1`, `counts/1`.
- J29. A file indexed while git reported it, then ignored (a `.gitignore` or `.git/info/exclude` entry added later), changes without git ever saying so. Its pending definitions were skipped as "changed since read, the next sync kicks again", but no sync ever came: vortex's private `docs/2026-10-19-closeout-resume.md` kept 9 vectors pending for days (2026-10-22). A full sync would not help either: a known, unlisted file that still exists is marked stale, and stale nodes still count as pending. Now the indexer notes each changed-unsynced path; when its queue runs dry it asks `Git.ignored/2`, deletes ignored files the listing leaves out, and re-reads ignored vendored ones (`Files.vendored?/1`), once per path and content.
- J30. An embedder pool whose devices differ about twentyfold (Polaris ~1,300 tokens/s, UHD 630 ~65) ran slower than Polaris alone: each `Embed.documents` call ended only when its last chunk did, so every batch of 48 waited ~22 s for the iGPU's one chunk of 4 while Polaris sat idle (72% of a 10-minute sample, 2026-10-22; pool 1.2 docs/s against Polaris alone ~3). Now a free embedder with no chunk left takes a backup copy of one still running elsewhere (fewest copies, then oldest); the first answer wins and the other copies are stopped, so the pool is never slower than its fastest device.
- J31. Every API request waits for a git sync (`fresh/1`, J19), but a sync with no graph changes still resolved the entire graph and rewrote its edges. On `~/vendor/llama.cpp` (26,819 nodes), Claude measured ~20 s per unchanged request with an empty sync selection and unchanged HEAD, against <70 ms for git status/diff; RPC and `:sys.get_state` samples found `Resolve.index` group/sort work and `Store.graph_snapshot` (2026-10-22). Now `sync_files/2` skips both resolution and the edge write only when parsed/deleted/stale counts are all zero and the previous resolution is known complete. Module upgrades and stale recovery force parsing; failed/interrupted syncs, store restarts and ignored-file deletions invalidate that knowledge, so even a zero-count retry resolves. Old hot-loaded indexers default conservatively to one resolve. J19 still waits for a sync that starts after the call and returns its generation and HEAD.
- J32. Prepare incremental edge resolution without enabling it: every changed or unresolved sync still does a tracked **full** resolve, recording source lookup read sets (misses, ordered path probes, certainty checks, and recursive re-exports included). File writes atomically maintain import/path/suffix lookup tables, a durable revision, changed-token and pending-source ledgers. Revision-checked source-scoped publication atomically replaces outgoing edges, coverage and reverse dependencies, including empty results; per-source output/read-set fingerprints retain unchanged coverage across revisions, and an edge comparison retains already-correct rows during coverage bootstrap or read-set-only changes. Dependencies use interned token/owner IDs with a compact indexed relation. Scoped replay keeps edge identities and SQL failures roll everything back. Embedding writes do not advance the resolution revision. Metadata and migrations live in SQLite, not closures in hot-loaded GenServer state. Missing lookup metadata is rebuilt from the stored snapshot on full publication, without reparsing files; the J31 no-change path remains and reads currentness through WAL without queuing behind the writer. J19 still binds replies to a reconcile started after the request. Seeded differential/read-set tests compare tracked results with the full oracle. The incremental selector remains disabled (stage 2).
